# Constitucion del Backend

## 1. Objetivo

Construir una API REST para Hotel Gran Capital que gestione clientes, autenticacion, habitaciones y reservas persistidas en PostgreSQL.

El backend debe centralizar las reglas de negocio. El frontend consumira la API, pero no podra sustituir sus validaciones ni su autorizacion.

## 2. Stack

- Lenguaje: TypeScript.
- Framework HTTP: Hono.js.
- Autenticacion: JWT.
- Hash de contrasenas: bcrypt con 8 saltos.
- Validacion: Zod.
- Base de datos: PostgreSQL.
- Driver PostgreSQL: pg.
- Runtime de despliegue: Node.js en Vercel.
- Pruebas: Vitest.

## 3. Compatibilidad con Vercel

Hono es compatible oficialmente con Vercel. La aplicacion debe exportar la instancia Hono como `default` desde `src/index.ts`.

Referencias oficiales:

- https://hono.dev/docs/getting-started/vercel
- https://vercel.com/docs/frameworks/backend/hono

El backend se ejecutara en runtime Node.js porque `bcrypt` y `pg` requieren compatibilidad con APIs de Node. No se utilizara Edge Runtime.

El desarrollo local podra ejecutarse con `vc dev` o mediante `tsx`.

## 4. Arquitectura

Se utilizara una arquitectura de tres capas:

```text
HTTP / Presentacion
        |
        v
Aplicacion / Servicios
        |
        v
Infraestructura / Persistencia
```

### Presentacion

Incluye rutas Hono, controladores, middleware, validacion de solicitudes y respuestas HTTP.

Los controladores no deben contener reglas de negocio ni consultas SQL.

### Aplicacion

Incluye casos de uso, servicios y reglas de autenticacion, reservas, cancelaciones e historial.

### Infraestructura

Incluye pool PostgreSQL, repositorios, BCrypt, JWT y configuracion de variables de entorno.

## 7. Autenticacion y autorizacion

El registro validara los datos con Zod y almacenara un hash BCrypt generado con 8 saltos.

El inicio de sesion verificara el hash y emitira un JWT con:

- Identificador del usuario.
- Usuario.
- Perfil.
- `jti`.
- Fecha de expiracion.

Perfiles:

- `administrador`.
- `cliente`.

Los usuarios registrados desde la API tendran perfil `cliente`. El usuario inicial `zumodev` tendra perfil `administrador`.

El cierre de sesion registrara el `jti` en `revoked_tokens`. El middleware rechazara tokens revocados.

## 8. Funcionalidades

### Registro de cliente

- Validar usuario y contrasena.
- Verificar usuario unico.
- Generar hash BCrypt.
- Crear usuario con perfil `cliente`.
- No devolver contrasena ni hash.

### Inicio de sesion

- Buscar usuario.
- Comparar contrasena con BCrypt.
- Generar JWT.
- Devolver datos publicos del usuario y token.

### Cierre de sesion

- Validar JWT.
- Revocar su `jti`.
- Impedir su reutilizacion.

### Reservar habitaciones

- Requerir autenticacion.
- Validar fechas.
- Verificar habitacion existente y disponible.
- Rechazar fechas superpuestas.
- Crear reserva confirmada dentro de una transaccion.

### Cancelar reserva

- Requerir autenticacion.
- Permitir al cliente cancelar sus propias reservas.
- Impedir cancelar una reserva ya cancelada o completada.
- Conservar la reserva para el historial.

### Actualizar reserva

- Utilizar `PATCH /api/reservations/:id`.
- Permitir modificar habitacion y fechas.
- Permitir al cliente modificar sus propias reservas confirmadas.
- Permitir al administrador modificar reservas confirmadas.
- Verificar nuevamente fechas, disponibilidad y superposiciones.
- Ejecutar la operacion dentro de una transaccion.
- No modificar reservas canceladas o completadas.

### Actualizar habitacion

- Utilizar `PATCH /api/rooms/:id`.
- Requerir perfil `administrador`.
- Permitir actualizar solo campos de habitacion definidos por el esquema.
- Rechazar precios invalidos y valores fuera de los catalogos permitidos.
- No permitir marcar como no disponible una habitacion con reservas confirmadas activas.

### Listar habitaciones

- Consultar habitaciones.
- Exponer cama, precio, disponibilidad y caracteristicas.

### Listar habitaciones por filtro

Filtros disponibles:

- Tipo de cama.
- Precio minimo.
- Precio maximo.
- Disponibilidad.
- Frigobar.
- Aire acondicionado.
- Televisor.
- Bano privado.

### Historial de reservas

- Mostrar reservas del usuario autenticado.
- Incluir reservas confirmadas, canceladas y completadas.
- Ordenar por fecha de creacion descendente.

## 10. Modelo de persistencia

Las tablas principales son:

- `RegistroDeCliente`.
- `habitacion`.
- `reserva`.
- `revoked_tokens`.

La vista `ListarHabitacionesPorFiltro` se mantiene como consulta de habitaciones.

La tabla `reserva` relaciona un cliente con una habitacion y conserva fechas, estado y datos de cancelacion.

La tabla `revoked_tokens` permite invalidar JWT al cerrar sesion.

## 11. Reglas de reservas

- `fecha_entrada` debe ser anterior a `fecha_salida`.
- La habitacion debe existir.
- La habitacion debe estar disponible.
- No puede existir una reserva confirmada superpuesta.
- Una reserva cancelada no bloquea nuevas reservas.
- La cancelacion es logica, no eliminacion fisica.
- La reserva debe pertenecer al cliente autenticado, salvo operaciones administrativas futuras.
- Una actualizacion de reserva debe excluir la propia reserva al comprobar superposiciones.
- Una habitacion con reservas confirmadas activas no puede marcarse como no disponible.

La superposicion se comprueba con:

```text
nueva_entrada < salida_existente
AND nueva_salida > entrada_existente
```

## 12. Fases de construccion

### Fase 1: Inicializacion

- Crear proyecto TypeScript.
- Instalar dependencias.
- Configurar Hono.
- Configurar exportacion compatible con Vercel.
- Configurar scripts de desarrollo y pruebas.

### Fase 2: Base de datos

- Configurar `DATABASE_URL`.
- Crear pool PostgreSQL.
- Ejecutar los scripts SQL.
- Crear repositorios.
- Probar consultas basicas.

### Fase 3: Infraestructura comun

- Validar variables de entorno con Zod.
- Crear errores de aplicacion.
- Crear middleware global de errores.
- Configurar CORS y headers de seguridad.

### Fase 4: Seguridad

- Implementar BCrypt con 8 saltos.
- Implementar firma y verificacion JWT.
- Implementar middleware de autenticacion.
- Implementar tokens revocados.
- Proteger respuestas sensibles.

### Fase 5: Clientes y autenticacion

- Implementar registro.
- Implementar login.
- Implementar logout.
- Implementar `/api/auth/me`.
- Probar credenciales invalidas y tokens revocados.

### Fase 6: Habitaciones

- Implementar listado.
- Implementar filtros.
- Validar parametros.
- Implementar consultas parametrizadas.

### Fase 7: Reservas

- Implementar creacion.
- Validar disponibilidad.
- Evitar superposiciones.
- Implementar transacciones.

### Fase 8: Cancelacion e historial

- Implementar cancelacion.
- Validar propietario.
- Implementar historial.
- Probar estados de reserva.

### Fase 9: Pruebas y despliegue

- Probar servicios y repositorios.
- Probar endpoints.
- Probar autorizacion por perfil.
- Configurar variables en Vercel.
- Verificar runtime Node.js.
- Probar con `vc dev` y despliegue.
